# TICKET — входящий запрос фичи

> Владелец: **Orchestrator**. Заполнено на шаге триажа (дизайн-док §6.1).

## Запрос
Сделать сервис для сохранения заметок: список заметок в двух видах — плитками (grid) и списком (list); базовое форматирование текста и поддержка markdown-разметки.

## Категория
full-stack (UI-фича)

## Маршрут
`full` — есть пользовательский интерфейс → нужен Designer (гейт 2: макет, опционально).

## Режим приёмки
с QA (отдельный `qa`-агент, не MVP).

## Что понятно / дано
- CRUD заметок: создание, чтение, редактирование, удаление.
- Переключение вида списка: «плитки» (карточки, grid) и «список» (rows), выбор сохраняется/переключается пользователем.
- Базовое форматирование текста (жирный, курсив, заголовки, списки и т.п.).
- Поддержка markdown-разметки: редактирование в markdown + превью (рендер).
- Один заметочный сервис с фронтендом и бэкендом (персистентность на сервере).

## Чего не хватает (открытые вопросы)
- Стек (бэкенд-язык, БД, фронтенд-фреймворк) — решит Planner; скиллы доступны: `python`, `typescript-node`, `go`, `postgres`, `react`, `docker`.
- Модель пользователей: один пользователь (local/одиночный) vs мультиюзер с авторизацией.
- Структура заметки: заголовок, содержимое, теги/категории, даты создания/изменения, закрепление (pin)?
- Поиск/фильтрация/сортировка заметок.
- Форма превью markdown: живой сплит-режим (редактор+превью) vs переключение «редактирование/просмотр».
- Хранение: серверная БД (persist) vs локальное хранение в браузере.

## Первый делегат
analyst → `SPEC.md`

## Решения гейта 1 (утверждено человеком)
- Модель пользователей: **мультиюзер + авторизация** (регистрация/вход/выход/сессия, ownership на сервере).
- Структура заметки: заголовок(опц.) + markdown + **теги** + createdAt/updatedAt.
- **Поиск по тексту + фильтр по тегам** (комбинируемые).
- Хранение: серверная БД (full-stack). Превью: live-сплит + переключатель.
- Восстановление пароля и верификация email — **вне MVP**.
