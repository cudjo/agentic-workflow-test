# PLAN: «Пепельный Бастион» — план реализации

**Статус:** ✅ Утверждён к исполнению (создан Planner, сессия 0, 2026-10-14)
**Основание:** `docs/SPEC.md` (гейт 1 ✅), `docs/DESIGN.md` + `docs/mockups/` (гейт 2 ✅).
**Задача:** реализовать пиксельную 2D метроидванию на Godot 4.x по утверждённым требованиям и макетам.

---

## 1. Резюме

| Параметр | Значение |
|---|---|
| Движок | **Godot 4.4+** (целевая 4.4/4.5; в окружении MCP ожидается 4.7) |
| Язык | **GDScript** (типизированный) — единственный язык проекта |
| Проект | `game/` (корень Godot-проекта), документация — `docs/` |
| Внутреннее разрешение | 480×270, целочисленное масштабирование, nearest-фильтр |
| Платформы | ПК: Windows Desktop, Linux |
| Стек-скилл | **`godot`** (добавлен в окружение; см. §10) |
| Конфигурация | `user://settings.cfg` (не env); Zero Dead Config (см. §7) |
| MVP | 5 зон, 3 способности, 5 боссов (2–3 фазы), 3 фракции, corpse run, 3 слота сохранений, RU+EN |

Метод: каждая задача — атомарная единица с acceptance-критериями, выполняемая одним Tasker'ом
в цикле «тест → код → запуск → итерация». Граф зависимостей в `docs/TASKS.json` оптимизирован
под параллельный запуск (см. §6).

### 2.2. Autoloads (порядок регистрации важен)

`EventBus → Config → Locale → InputManager → AudioManager → GameState → FactionManager →
Journal → SaveManager → SceneRouter`.

Правило: **данные — в `data/` ресурсах**, состояние — в autoload'ах и `GameState`, передача —
сигналами `EventBus`. Autoload'ы не рисуют UI.

### 2.3. Слоевая модель сцен

`Main.tscn` → `WorldRoot` (текущая зона) + `HUD` (CanvasLayer 10) + `UI` (20) + `Toasts` (30)
+ `Overlay` (40). Переход зоны заменяет только `WorldRoot` (см. DESIGN §4.4).

## 3. Ключевые технические решения

### 3.1. Физика и тайминги (детерминизм)
- `CharacterBody2D` + `move_and_slide()`, гравитация применяется вручную; `physics_ticks_per_second = 60`.
- Все игровые тайминги — из `data/balance/balancing.tres` (единый источник, DESIGN §7/AC-01.2).
  Предлагаемые стартовые значения (уточняются при балансировке):

| Параметр | Предложение | Обоснование |
|---|---|---|
| `V_walk` | 90 px/s | ~5.6 тайла/с при тайле 16 px |
| `H_jump` | 32 px (2 тайла) | классика метроидвании |
| `t_apex` | 0.35 s → `vy0≈183`, `g≈523` px/s² | вывод по формуле `vy0=2H/t`, `g=vy0/t` |
| `H_double` | 0.8·H_jump (AC-02.1) | требование |
| `D_dash` / `T_dash` / `C_dash` | 48 px / 0.15 s / 0.6 s | `C_dash ≤ 1 s` (AC-02.2), i-frames |
| `V_wall_slide` | 40 px/s | AC-02.3 |
| `T_parry` | 0.18 s | 150–200 мс (DESIGN §7) |
| `E_attack`/`E_block`/`E_roll` | 12 / 8 / 10 | трата выносливости |
| `t_death` | 1.2 s | AC-05.2 (источник — баланс) |

- **Coyote time 0.1 s**, **jump buffer 0.15 s** (AC-01.4), **i-frames** dash/roll.
- Прерывание состояний: `Death > Hurt > Roll/Dash > Attack/Block > Jump/Fall > Run > Idle` (DESIGN §7).

### 3.2. Ввод
- Действия в `project.godot` InputMap; ремап пользователя — поверх, в `user://settings.cfg`
  (AC-01.3). Определение активного устройства (`InputEventKey`/`InputEventJoypadButton`/PS/Xbox)
  → переключение глифов подсказок (EC-08).
- Единый буфер ввода 150 мс на действия игрока **и** на подтверждения меню (DESIGN §9.2).

### 3.3. Способности
- `ability_base.gd` — интерфейс `activate()`, флаги состояния; `GameState.abilities` — набор.
- Двойной прыжок — сброс при приземлении; Dash — i-frames + кулдаун; Карабканье — slide + wall kick.
- **Ability gates** (`world/props/ability_gate.tscn`) — физический блок + `Node2D`-подсказка
  «Нужно: …» над препятствием (AC-02.4), без скрытой блокировки.

### 3.4. Сохранения и смерть
- Формат: JSON в `user://saves/slot_{1..3}.json` + заголовок `{schema_version, checksum}`.
- **Атомарность:** запись в `slot_N.json.tmp` → `DirAccess.rename` поверх (EC-14: старый файл цел).
- **Целостность:** SHA-256 тела через `HashingContext`; несовпадение → слот «повреждён», выбор
  другого (EC-07), без вылета. Миграции по `schema_version`.
- Сохранение **только у костра** и **запрещено в бою** (Q3, EC-06) — `GameState.in_combat`.
- Смерть (AC-05.2/05.3): инвентарь+валюта складываются в `Corpse`-метку на месте гибели;
  возрождение у последнего костра с полным HP; подбор по контакту; повторная смерть до подбора
  делает потерю необратимой (EC-05). Выход в бюджет смерти = обычная смерть (EC-04).

### 3.5. Локализация и доступность
- RU/EN: `assets/locale/{ru,en}.csv` + `TranslationServer`, весь UI через `tr(key)`;
  проверка переполнения обеих локализаций (DESIGN §9.6 п.6).
- Токены `Config`: масштаб UI 100/150/200% (через `font_size`/контейнеры, шаг 8 px),
  «читаемость силуэтов», «без мигания» (≤3 вспышки/с), «субтитры звуков», язык, режим окна.
- Шрифт: **Press Start 2P** (OFL, «не для продажи») как `FontFile` в `assets/fonts/`.

### 3.6. Освещение/атмосфера
- `CanvasModulate` (ambient 0.26–0.5) + `PointLight2D`; постеризация/дизеринг Байера 4×4 шейдером
  на слое (DESIGN §8.7). Эмиссивные объекты (небо/луна/окна/пламя) не затемняются.
- Палитры зон — из DESIGN §8.6; силуэт героя всегда читаем (AC-07.1) через контурный шейдер.

## 6. Параллелизм и зависимости

- `dependsOn` в `docs/TASKS.json` — **только реальные** зависимости (данные/контракты или конфликт
  файлов). Задачи без общей зависимости оставлены независимыми для параллельного запуска.
- Orchestrator запускает до **2** фоновых задач одновременно.

**Безопасно параллелить (разные файлы/слои, нет общих контрактов):**
- **T-03 и T-13** — InputSystem vs тайлсет-пайплайн: независимы (после T-01).
- **T-05 и T-06** — визуал игрока vs AbilitySystem: общий `Player.tscn`, поэтому даны общие
  зависимости через T-04, но при согласованном контракте (FSM-состояния) их можно параллелить.
- **T-18 и T-25** — UI-компоненты vs SaveManager: независимы (после T-01).
- **T-27 и T-29** — фракции vs прогрессия: общий `GameState`, но разные поля; параллелимы после T-25.
- **T-34 и T-35** — аудио vs освещение: независимы (после T-01/T-13).
- **T-15 и T-16** — зоны 2–3 vs зоны 4–5: независимы после T-13.
- **T-30 и T-33? — НЕТ:** карта (T-33) требует зон; см. ниже.

**Строго последовательно (реальные контракты):**
- `T-01 → T-02…` — всё зависит от каркаса проекта.
- `T-03 → T-04 → T-05` — игрок невозможен без ввода, анимация — без состояний игрока.
- `T-06 → T-07/T-08` — dash и wall climb используют `ability_base` из T-06.
- `T-10 → T-11/T-12` — блок и враги используют боевое ядро (damage/hitbox).
- `T-13 → T-14/T-15/T-16` — зоны строятся на тайлсет-пайплайне.
- `T-25 → T-26/T-27` — смерть и фракции персистятся SaveManager'ом.
- `T-30 → T-31/T-32` — боссы используют boss framework.
- `T-17` (переходы) — после первой зоны (T-14): нечего переключать раньше.
- `T-33` (карта) — после зон (T-13, T-17).
- `T-37` (QA) — финальный сквозной пасс после всех систем.

## 7. Конфигурация и безопасность (Zero Dead Config)

- **Нет `.env`/`docker-compose`:** игра локальная, серверной части нет. Единственный источник
  настройки — `user://settings.cfg` (ConfigFile), читается `Config.gd`.
- Правило **Zero Dead Config:** каждый ключ в `project.godot` и `user://settings.cfg` обязан
  иметь потребителя в рантайме. Ключи `Config.gd` и их потребители:

| Ключ | Потребитель |
|---|---|
| `language` (ru/en) | `Locale.gd` → `TranslationServer.set_locale` |
| `ui_scale` (100/150/200) | `Theme` (`font_size`/контейнеры) |
| `window_mode` | `DisplayServer.window_set_mode` |
| `silhouette_readability` | `silhouette_outline.gdshader` + виньетка |
| `no_flash` | мерцание HP/факелов, вспышки урона, тряска, печать текста |
| `sound_subtitles` | `AudioManager` → тост-субтитры значимых звуков |
| `master/music/sfx_volume` | `AudioServer` шины Master/Music/SFX |

- **Безопасные прод-дефолты:** в экспортной сборке (`OS.is_debug_build()==false`) отключены
  отладочный вывод, читы (телепорт/noclip), dev-оверлеи; ошибки не показываются игроку сырым стеком.
  Debug-инструменты существуют только в debug-сборке (нет «мёртвых» дев-флагов в релизе).
- Мёртвых ключей нет: если ключ не используется — он не добавляется.

## 8. Риски и меры

| Риск | Митигация |
|---|---|
| Godot не установлен в окружении (`C:\Program Files\Godot\Godot.exe` отсутствует) | `docs/init.sh` проверяет рантайм и сообщает; установить Godot 4.4+ / задать `GODOT_PATH` до этапа 1 |
| Ассеты/арт отсутствуют (свой + CC0) | На время разработки — программные заглушки (цветные прямоугольники) за тем же контрактом сцен; замена — без изменения логики |
| Тайминги физики «плывут» между машинами | Единый `balancing.tres`, физика 60 Hz, тесты на константы из ресурса |
| Кириллица в Press Start 2P переполняет панели | Тест переполнения RU/EN в T-18/T-36 (DESIGN §9.6) |
| Разрастание фичи (5 зон, 5 боссов) | Строгая атомарность задач, ранний вертикальный срез (этапы 1–4) для e2e |
| Ошибки сохранения теряют прогресс | Атомарная запись + checksum + миграции (T-25), EC-07/EC-14 |

## 9. Definition of Done

- Все acceptance-критерии задач из `docs/TASKS.json` выполнены и проверены.
- Сквозной проход: меню → зона 1 → способности → бой → сохранение/смерть → фракции → боссы →
  финал, без падений; сохранение/загрузка восстанавливает состояние (AC-05.1).
- a11y-чек-лист DESIGN §9.6 пройден; NFR: 60 FPS в бою с 5 врагами, загрузка зоны ≤3 с.
- CI зелёный (импорт + GUT-тесты headless), экспорт Windows/Linux собирается.
